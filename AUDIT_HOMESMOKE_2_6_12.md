# HomeSmoke 2.6.12 — ревизия основной Android-программы

Дата ревизии: 2026-09-07.

## Жёсткие границы

- Arduino и файлы `arduino/` не изменялись.
- Подтверждённые команды и формат телеметрии не изменялись.
- MQTT-команды/поля Remote 2.0 не переименовывались и не расширялись.
- Auto-программы v1/v2 и их текущая структура сохранены.
- Android 4 / Legacy не возвращается в разработку или CI.
- Основная поддерживаемая версия — Android 6+ (`minSdk 23`).

## Исправлено в 2.6.12

1. ACK удалённой уставки теперь гарантированно истекает по `controller_ack_timeout` даже если после команды телеметрия полностью пропала. Раньше timeout проверялся только при приходе следующего пакета Arduino.
2. Добавлены unit-тесты `CommandAckManager` для `applied`, timeout без телеметрии и `bluetooth_disconnected`.
3. MQTT-клиент получил keepalive watchdog: полуоткрытое соединение без входящих MQTT-пакетов больше не может бесконечно считаться живым.
4. Устранена гонка MQTT connect/stop: завершившаяся старая попытка подключения не может самопроизвольно восстановить MQTT после нажатия «Отключить».
5. Ошибка публикации telemetry/ACK закрывает повреждённый MQTT transport и запускает штатный reconnect.
6. После потери Bluetooth очищается `latest` telemetry, поэтому основной экран не выдаёт старые значения за актуальные данные текущего соединения.
7. Нажатие на foreground notification теперь открывает фактический launcher `ModernHomeSmokeActivity`, а не базовый `MainActivity`.
8. Библиотека Auto-программ сохраняет предыдущую JSON-копию; при повреждении основной записи сначала выполняется восстановление из backup вместо немедленного перехода к программе по умолчанию.
9. Прореживание истории для графика теперь строго ограничено запрошенным количеством точек и всегда сохраняет начало/конец процесса.
10. CI расширяется тестами основной Android-логики и проверками перечисленных инвариантов.

## Найдено, но намеренно не изменено без отдельной проверки

### Auto: активация щупа после стабилизации
Сейчас `AFTER_CHAMBER_READY` зависит от текущего `chamberReady`. Если камера после первой стабилизации снова выйдет из допуска, контроль щупа временно перестаёт выполнять условие завершения. Формулировка UI «контроль щупа начнётся после стабилизации» может подразумевать одноразовую активацию (latch). Это изменение повлияет на реальную логику приготовления, поэтому оставлено до отдельного решения по результатам полевого теста.

### Auto: большие разрывы телеметрии
`AutoEngine` суммирует интервал между соседними пакетами, если камера была и остаётся в допуске. При редком случае длительной тишины канала без фактического разрыва Bluetooth такой интервал может попасть в выдержку. Ограничение/cutoff потребует согласования, потому что меняет тайминг существующих программ.

### MQTT STOP ACK
Текущий Remote-протокол `stop -> stop_sent` оставлен без изменения. Менять состояния ACK или добавлять новые поля без прямого разрешения нельзя.

### Presentation layer
Одновременно существуют `HomeSmokeApplication/UiPolish` и `ModernHomeSmokeActivity`, оба выполняют динамическую стилизацию дерева View. Это технический долг и потенциальный источник лишних layout-pass. Консолидацию лучше выполнять отдельной UI-версией после визуальной проверки на реальном устройстве, чтобы не сломать текущий подтверждённый внешний вид.

### История
История Auto хранится локально без автоматической очистки. Автоудаление не добавлено, чтобы приложение самостоятельно не удаляло пользовательские процессы. В дальнейшем безопаснее добавить ручное удаление/экспорт либо настраиваемый retention.

## Приоритет следующего полевого теста

1. Bluetooth disconnect/reconnect во время PID и Auto.
2. MQTT отключение/включение сети на 1–3 минуты с последующим восстановлением.
3. Remote setpoint при пропавшей телеметрии — ожидается финальный `controller_ack_timeout`.
4. Нажатие foreground notification при свёрнутом HomeSmoke.
5. Поведение Auto `AFTER_CHAMBER_READY`, если после стабилизации камера временно вышла из допуска.
