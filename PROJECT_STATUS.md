## Готово

- Основной HomeSmoke восстановлен как отдельное Android-приложение с Bluetooth, MQTT, PID, Auto до четырёх этапов, историей, графиками и полевой диагностикой.
- В HomeSmoke добавлены Kotlin-файлы диагностики; основная программа пока остаётся гибридной Java/Kotlin.
- HomeSmoke Remote полностью переведён с Java на Kotlin; современный экран реализован на Jetpack Compose.
- Добавлены светлая, тёмная и системная темы, адаптация узких экранов и тесты Compose-разметки.
- Android Auto приведён к установленной Arduino: `a1` один раз на старте, затем `kNN`; `a2`, `x1`, `x0`, `h` не отправляются; STOP — `a3`.
- После каждой Auto-уставки HomeSmoke ждёт свежую телеметрию `mode=1` и подтверждённую уставку; таймер этапа до подтверждения не идёт.
- История и графики записывают сессии Auto, PID и ручного режима; для Auto сохраняются этапы, для ручных режимов — телеметрия и события режима.
- Основная иконка HomeSmoke заменена на логотип Home Bizard Smoke; добавлены обычный и адаптивный варианты для Android.
- Remote-команда уставки проходит цепочку Remote → HomeSmoke → Arduino и получает финальный ACK `applied` либо ошибку/тайм-аут контроллера.
- В Remote 2.4.7 отправка MQTT-команд уставки и STOP вынесена из UI-потока в отдельный executor; после корректировки CI версия успешно собрана и опубликована workflow.
- Для Remote 2.4.8 подготовлена отдельная launcher-иконка Home Bizard Smoke Remote с визуальным признаком беспроводной связи.
- Полевой тест HomeSmoke 2.6.18 от 10.09.2026 предварительно успешен: основное приложение отработало без воспроизведённых ошибок по наблюдению владельца.
- Сборка обеих программ автоматизирована в `.github/workflows/build-homesmoke.yml`.
- Неиспользуемые ESP32/PlatformIO и Arduino rev2 сохранены только в `archive/firmware-not-used/` и не относятся к активной сборке.
- Одноразовые скрипты прошлых миграций сохранены в `archive/ci-migrations/` и не выполняются CI.

## Полевой дефект Remote и исправление 2.4.8

Полевой тест 10.09.2026 воспроизвёл периодическую потерю связи HomeSmoke Remote при работе приложения в фоне.

По текущему коду MQTT-соединение принадлежит `MainActivity`. `MqttClient` отправляет `PINGREQ`, но версия 2.4.7 не контролирует срок получения `PINGRESP` и может некоторое время считать half-open socket подключённым. В Remote 2.4.8 внесено минимальное исправление без изменения MQTT/Arduino-протокола:

- учитывать время последнего входящего MQTT-пакета;
- отслеживать незавершённый `PINGREQ` и срок `PINGRESP`;
- признавать зависшее соединение неактивным, чтобы существующий reconnect-механизм выполнил переподключение;
- существующий трёхсекундный health-loop использует новый статус `isConnected` и запускает reconnect после выявления зависшего соединения;
- сохранить точные байты существующих MQTT publish/subscribe пакетов отдельным тестом.

Это исправляет обнаружение и восстановление зависшего соединения, но само по себе не гарантирует непрерывную работу MQTT при длительном deep-background/Doze или уничтожении процесса Android. Если повторный полевой тест подтвердит именно такую необходимость, foreground-service следует делать отдельной задачей без смешивания с текущим минимальным fix.

## Неизменяемые ограничения

- В проекте HomeSmoke нет ESP32; не подключать ESP-протокол из другого проекта.
- Arduino сейчас не перепрошивается; файл rev2 в архиве не является установленной прошивкой.
- Не отправлять Arduino-команды, не подтверждённые старым протоколом.
- Android Auto выполняется телефоном; Arduino используется как PID-исполнитель.
- Не использовать встроенный Arduino Auto `a2`.
- Сохранять буквальный терминатор `\\0` и формат телеметрии `|...|end`.
- `k` и `v` принимают только целые значения 0–100.
- Сохранять package id приложений и совместимость библиотеки Auto-программ.
- Android 4/5 не возвращать; текущий минимум — Android 6.
- Не изменять `main` и не сливать ветки без прямого разрешения владельца.
- Не удалять файлы, не публиковать изменения в GitHub и не менять версии приложений без прямого разрешения владельца.
- Сохранять HomeSmoke 2.5.0 как резервную установочную сборку.

## Правило версий

- Любое изменение поведения или интерфейса конкретного приложения повышает его `versionCode` минимум на 1 и `versionName` минимум на patch-версию.
- Документация, архивирование и изменения CI без изменения APK не повышают версии приложений.
- Номер версии берётся из `app/build.gradle` или `remote/build.gradle`; интерфейс не должен содержать вручную зафиксированный номер.
- Каждая новая версия получает отдельную запись в `CHANGELOG.md` и обновление этого файла.
